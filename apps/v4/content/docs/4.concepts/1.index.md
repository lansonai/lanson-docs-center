LansonAI is the **Voice Context Layer for Live Speech**. A Voice Context Layer sits between live speech recognition and the application that consumes it. Developers access this capability through **Lanson Live API**.

**Realtime**, **Segment**, and **Batch** are three integration paths of Lanson Live API:

| Plane | Who segments speech |
|---|---|
| Realtime WS | Server (VAD on PCM stream) |
| Segment HTTP | **Client** (you POST each utterance clip) |
| Batch jobs | Server (time-based slicing of `audio_url`) |

Its job is not simply to produce words.

Its job is to turn continuously changing speech into **usable context**.

## Speech recognition is only the first layer

A speech recognition system may produce something like:

```text
I think we should meet on
I think we should meet on Thursday
I think we should meet on Thursday afternoon
I think we should meet Thursday afternoon instead
```

Each output may be reasonable at the moment it was generated.

But an application has different questions:

- Which text should already be visible?
- Which text may still change?
- When is a thought complete enough to translate?
- When should downstream logic act on it?
- How should corrections appear without disrupting the reader?

Those questions exist above recognition itself.

That is the problem addressed by the Voice Context Layer.

## From audio to usable context

Conceptually, a live speech system can be viewed as:

![From Audio to Usable Context: Voice Context Layer](/images/docs/voice-context-layer-flow.png)

The recognition layer determines what was likely spoken.

The Voice Context Layer determines how that evolving information should become usable by the application.

This may include:

- stabilization
- contextual correction
- segmentation
- translation readiness
- presentation continuity
- lifecycle state

## Why this matters

For offline transcription, the system can wait until the audio has finished before producing the final result.

Live applications cannot.

They must continuously balance two competing goals:

**Responsiveness**

Show useful information as soon as possible.

**Stability**

Avoid repeatedly changing information the user has already read.

LansonAI is designed around that tradeoff.

The objective is not simply to make text appear faster.

It is to make live speech **ready to use while it is still happening**.

## Technology layers

| Name | Role |
|---|---|
| **LansonAI** | Company and platform: Voice Context Layer for Live Speech |
| **Lanson Live API** | Developer interface to the Lanson Live speech model, `lanson-live-1` |
| **Trinity Engine** | Multi-model orchestration, speech processing, and context coordination |
| **StableStream™** | Continuous, stable, readable live text |
| **LiveFinal™** | Progressive correction and segment finalization |

- **[Trinity Engine](/docs/concepts/trinity-engine)** — multi-model orchestration, speech processing, and context coordination.
- **[StableStream™](/docs/concepts/stablestream)** — continuous, stable, readable live text.
- **[LiveFinal™](/docs/concepts/livefinal)** — progressive correction and segment finalization.

These names explain how Lanson Live works. They are not three selectable models, and concept diagrams are not additional event schemas. The [API reference](/docs/api-reference) defines the messages you can send and receive.

## API and App

**Lanson Live API** is for developers building speech into their own applications. **Lanson Live App** is the end-user product for live speech experiences. They share Trinity Engine, but the App's behavior is not an API contract.

Lanson Flow, Lanson Live App, Lanson Reception, and Lanson Podcast are product lines for different speech use cases. The [Developer panel in Lanson Live App](https://live.lansonai.com/?panel=developer) lets you create and manage API keys. To start integrating, follow [Get started with Lanson Live API](/docs/start/quickstart).
