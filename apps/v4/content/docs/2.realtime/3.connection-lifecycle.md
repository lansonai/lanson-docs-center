The full lifecycle of a realtime WebSocket connection.

## Stages

![Realtime WebSocket Connection Lifecycle](/images/docs/connection-lifecycle-flow.png)

## 1. Connect

WebSocket handshake:

- Server-side: `Authorization: Bearer sk-...` header
- Browser: `?access_token=rt_...` query parameter

Conditions checked on connect:
- WebSocket upgrade required (else 426)
- Gateway enabled (else 503 `gateway_disabled`)
- Connection quota passes (concurrent + rate)

## 2. session.created

Received immediately on connect:

```json
{
  "type": "session.created",
  "session_id": "sess_...",
  "limits": {
    "max_concurrent_utterances": 2,
    "max_session_seconds": 900,
    "idle_timeout_seconds": 60,
    "remaining_audio_seconds": 3600
  }
}
```

## 3. Configure (optional)

Send `session.update` to set parameters:

```json
{ "type": "session.update", "language": "zh" }
```

The gateway applies the configuration and confirms it with `session.updated`. Configure optional refinement and translation before audio; see [Session Configuration](/docs/realtime/session-configuration).

## 4. Stream audio

Continuously send PCM16LE audio frames:

- Text frames: `input_audio_buffer.append` (base64 JSON) — the supported transport today
- Binary frames: not transcribed by the public gateway today; use base64
- Speech boundaries: detected by server-side VAD as you continue sending audio, including natural pauses

## 5. Receive events

1. `input_audio_buffer.speech_started` — Voice Activity Detector detects speech onset.
2. `input_audio_buffer.speech_stopped` — VAD detects silence or segment boundary.
3. `conversation.item.input_audio_transcription.completed` — Final stable transcription payload emitted.

This cycle repeats for each speech segment.

## 6. Close / Reconnect

### Normal close

Client calls `ws.close()` after receiving expected utterance results. Closing finalizes usage accounting, but is not a guarantee of pending transcript delivery or a session-wide final event. See [LiveFinal™](/docs/ai-native-transcription/livefinal).

### Timeout close

| Close code | Cause / close reason | Trigger |
|---|---:|---|
| 4408 | `idle_timeout` | No audio received within `idle_timeout_seconds` |
| 1008 | `session_duration_limit` | Exceeded `max_session_seconds` |
| 1008 | `session_audio_limit` | Exceeded `max_audio_seconds_per_session` |
| 1008 | `audio_quota_exhausted` | Billing-window audio budget exhausted |
| 1009 | `frame_too_large` | Single frame exceeds 1 MiB |
| 1011 | `client_error` / internal error | Client socket error or unexpected gateway failure |

## Idle timeout

To avoid idle timeout, either:
- Send silent frames to keep the connection alive
- Or close explicitly and reconnect when needed

## Recommended reconnect design

1. Listen for `close` events, decide reconnect based on close code
2. 4408 (idle) and 1008 (duration limit): reconnect directly
3. 1000 (normal): do not reconnect
4. After reconnect, re-send `session.update` to restore configuration

See [Reconnect a Live Session](/docs/guides/reconnection) for a detailed guide.
