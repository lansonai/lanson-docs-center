Recording pipeline — never lose a finished recording

Why we rebuilt ingest conflict checks, finalize, and postprocess around the rule "MP4 on disk means done", so transcription or remux races can no longer wipe out a finished programme.

What broke before

A finished recording could be marked failed for three reasons that had nothing to do with whether the video was actually on disk:

  1. Remux race. finalize() ran synchronously the moment pipeline.stop() resolved. ffmpeg was often still flushing its .temp.mpegts into the final .mp4. The size check read 0 bytes, the record was written as failed, and the user saw a red "录制失败" card even though a playable MP4 existed seconds later.
  2. Transcription / postprocess failure. A 4xx from the Audio v1 API, an R2 permission change, or a queue overflow wrote record.state = "failed". The MP4 was fine; the card went red anyway. Transcription failed is not the same as recording failed.
  3. Back-to-back ingest 409. A partner scheduling two episodes two minutes apart on the same channel got 409 "recording already exists for this source or episode and time window". The 5-minute padding guard meant consecutive programmes always collided.

What we changed

1. hasIngestJobConflict — padding only for the same episode

Keeps the 5-minute padding for the same episode (so a duplicate partner submit of the same window is still rejected) but uses real window overlap for different episodes on the same source (so back-to-back episodes with a 2-minute gap are now accepted).

2. createIngestJob — active-source guard only when the window is due

Only applies the active-source guard when the window opens within 60 seconds. A future job is no longer blocked by an active session that is still recording the previous programme.

3. registry.finalize — release synchronously, persist asynchronously

The synchronous part releases the source identity, stops the subtitle timer, and marks the session finalized. The asynchronous finalizeAsync waits for the remux to land on disk via the new sizeAfterFinalize() helper (up to 2 seconds, polling every 100 ms) and then runs hasPlayableMp4() to decide done vs failed.

4. hasPlayableMp4() — the single source of truth

If the MP4 file is non-empty on disk, the recording is done. Pipeline status, ASR health, transcription cues, and postprocess state are not part of the decision.

5. postprocess.runPostprocess — failures stay in postprocess

Writes failures only into postprocess.state and postprocess.error. It no longer touches record.state. If a record was previously written as failed but its MP4 still exists on disk, the postprocess pass heals it back to done (the same invariant reconcileOrphans uses on startup).

6. segments.ts — skip empty segments in the offset chain

Skips segments with durationMs <= 0 when computing the cue offset, so a stalled segment can no longer poison the cue timeline of the segments that follow it.

How we know it works

Three independent rounds of verification were run against bce486b.

Round 1 — repository tests

bun test server/live shows the same pass/fail signature as the pre-change baseline (53 pass / 13 fail / 9 errors; the 13+9 are pre-existing Bun node:test nested-test limitations, not regressions). New regression tests cover back-to-back episodes, same-episode padding preservation, real-window- overlap blocking, remux waiting, and postprocess-failure preservation.

Round 2 — end-to-end against the business functions (isolated RECORD_DIR)

Operational notes

  • abortUnproductive still exists but is now consistent with the new finalize path: if any frames reached the MP4 before the 45-second empty watchdog fires, the recording is preserved as done. If truly zero bytes, it is failed as before.
  • The 3-minute stall watchdog is unchanged. It still force-stops a live source that stops producing audio, so we never have an indefinite "recording" hanging forever. The new finalize makes sure we don't lose the bytes we did capture.
  • Compression and subtitle generation remain separate failures. If RECORDING_COMPRESS fails or Audio v1 returns an error, the user still sees the recording; only the postprocess status is red.

Rollback

git revert bce486b
git push origin main

The only invariant the new code introduces is "MP4 on disk implies done". A revert takes the system back to "whatever finalize wrote in the first few milliseconds after stop", which is the pre-fix behaviour.
